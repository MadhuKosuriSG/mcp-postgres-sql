- (constraint) Existing codebase is a layered FastAPI service: api/ (HTTP routers) -> services/ (business logic) -> mcp_server/ (MCP client/lifecycle). core/ package exists but is empty. Any new auth code should fit this layering unless a real trade-off says otherwise.
- (constraint) No in-repo DB layer exists today - all Postgres access is proxied through the external postgres-mcp MCP server (launched via uvx subprocess). Brainstorm goal calls for SQLAlchemy/Alembic in-repo for user registration, which would be the first direct DB ownership this repo has.
- (constraint) No authentication/authorization exists on any current endpoint (POST /chat, POST /mcp/call, GET /health, GET /).
- (question) Who is this auth for: real end-users registering accounts (product-facing), or is the actual goal to protect the /chat and /mcp/call endpoints themselves (service-to-service / operator auth)? Carried over unanswered from bmad-prd brain dump.
- (version) FastAPI 0.119.1, Uvicorn 0.35.0, mcp SDK 1.28.1, openai (AsyncOpenAI) >=1.0.0,<2.0.0, python-dotenv 1.1.1 - current stack per docs/architecture.md scan.
- (decision) AD-candidate: Auth is for real end-users (product-facing accounts) - identity matters downstream (per-user chat history, permissions on what they can ask the LLM/MCP tools to do). Not just endpoint/service protection. Prevents building a thin API-key/service-auth layer when a full user identity model is actually needed.
- (decision) AD-candidate: New auth/user code owns direct Postgres access (SQLAlchemy + Alembic), separate from the existing postgres-mcp MCP proxy path. Binds: user table CRUD, migrations, and credential storage go through the app's own DB layer, never through MCP execute_sql-style tools. Prevents: password/credential writes going through a generic LLM-facing SQL-execution tool (security/transactional-integrity risk), and prevents two DB-access paradigms competing for the same tables.
- (decision) AD-candidate: Session strategy is JWT (stateless signed access tokens), not server-side sessions. Binds: auth issues/validates JWTs, no session store/Redis introduced for auth state. Prevents: a later builder introducing a parallel session-store mechanism for the same login state.
- (decision) AD-candidate: This pass scopes to registration only (create account, hash+store password, enforce uniqueness/validation). Login/JWT issuance is planned direction (per AD: JWT session strategy) but out of scope for this build - Binds: no /login endpoint or token issuance in this pass. Prevents: scope creep into login/token-refresh flows before registration itself is solid.
- (decision) AD-candidate: Auth code follows the existing repo pattern rather than a new self-contained package. Router in api/auth.py, business logic in services/auth_service.py. core/ (currently empty) becomes the home for cross-cutting infra: SQLAlchemy async engine/session setup and the User ORM model. Binds: any future feature needing direct DB access reuses core/'s engine/session, not a duplicate. Prevents: a second DB-engine setup being invented by a later feature.
- (version) Password hashing: Argon2id via argon2-cffi (OWASP current recommendation for new projects, verified via web search 2026-07-14), not passlib/bcrypt. No existing hashing convention in repo to preserve.
- (decision) AD-candidate: DB access uses SQLAlchemy async engine with asyncpg driver, consistent with the rest of the app being async-native (AsyncOpenAI, MCP async client session). Prevents a sync DB call blocking the event loop.
- (constraint) New SQLAlchemy engine reads the same DATABASE_URI env var postgres-mcp already uses - single source of DB connection config, not a second possibly-drifting one.
- (decision) AD-candidate: Auth service errors map to real 4xx HTTP status codes (409 duplicate email, 422 invalid input, etc.) via HTTPException, diverging from the existing blanket 502-on-service-error pattern (which is correct for MCP/tool failures but wrong for auth's client-caused errors). New pattern for this repo - flagged explicitly so it isn't flattened back to 502-for-everything.
- (direction) Deferred: no automated test suite is introduced for this pass. Registration ships without pytest/test-DB coverage; testing strategy remains an open item for a future pass, not decided here.
- (direction) Deferred: deployment/environment envelope (Dockerfile, CI/CD, migration-execution strategy for Alembic) is out of scope - no deployment config exists anywhere in this repo yet, and this feature doesn't force a decision. Alembic migrations exist as files; how/when they run in any deployed environment is unresolved.
- (decision) AD-candidate: User entity fields for registration: email (unique), username (unique, separate from email), full_name, phone_number, hashed_password, plus id + created_at. Binds: the users table/User model shape. Prevents: a later builder assuming email-only identity or bolting on username/phone as an afterthought migration.
- (version) Verified via web search 2026-07-14: SQLAlchemy 2.0.51 (stable 2.0 line; 2.1 still beta, stay on 2.0.x), asyncpg 0.31.0, alembic 1.18.5, argon2-cffi 25.1.0.
- (event) Reviewer gate run: lint_spine.py clean (0 findings); 2 reconcile agents (PRD/brainstorm, brownfield docs) - both confirmed spine ratifies sources with no contradictions; rubric walker, web-verification, adversarial, and security lenses run in parallel.
- (decision) AD-8 (new, from adversarial review): core/db.py's AsyncEngine is constructed and disposed via FastAPI's lifespan hook, mirroring the existing MCPManager pattern - not eager module-level construction. services/auth_service.py obtains a per-request AsyncSession via FastAPI Depends, never a shared/singleton session across requests. Prevents: two builders each satisfying AD-5/AD-6 literally while one uses a singleton session (concurrency corruption risk) and the other a per-request session.
- (decision) Tightened AD-7 (from adversarial review): duplicate email/username is detected via insert-then-catch IntegrityError against the DB unique constraint, not check-then-insert (avoids a TOCTOU race under concurrent registrations that could fall through to the 502 path). detail stays a flat string, not a structured/field-keyed object.
- (decision) Tightened DATABASE_URI convention (from adversarial review): core/db.py reads DATABASE_URI through the existing config.py loader (extended, not a parallel os.environ.get() call) - keeping exactly one code path reading the var, not just one env var name.
- (decision) New convention (from security review): registration's success response returns only non-sensitive fields (id, email) - phone_number, full_name, and hashed_password are never echoed back in any API response.
- (decision) New rule on AD-7 (from security review): registration validates a minimum password length before hashing (reject too-short passwords with 422), rather than hashing whatever is submitted.
- (direction) Deferred (expanded, from rubric-walker + web-verify reviews): JWT signing-secret storage/rotation, and token revocation/logout strategy - both unresolved, to be decided when login/JWT is actually designed (AD-3's direction, not this pass).
- (direction) Deferred (new, from security review): email/username-enumeration hardening - AD-7's 409-on-duplicate response currently does reveal whether an email/username is already registered; whether to soften this (generic message) for enumeration resistance is an open UX/security trade-off, not decided here.
- (question) BLOCKER (from adversarial + security review, both independently found this): AD-2 draws a code-level boundary ('auth code never uses postgres-mcp'), but postgres-mcp's execute_sql tool is invoked with the same DATABASE_URI/DB role as the new SQLAlchemy layer, with no DB-level restriction. Once the users table exists, the existing /chat LLM tool-calling path can already run execute_sql SELECT against it and read hashed passwords/PII directly - nothing stops this today. AD-2 alone (a code convention) does not close this. Needs a DB-level fix (e.g. a separate, restricted Postgres role/grants for postgres-mcp's connection that excludes the users table) or an explicit accepted-risk call for this MVP. Surfaced to user before close.
- (decision) Blocker resolved: user explicitly accepted the postgres-mcp/users-table DB-role risk for this MVP rather than restricting the DB role now. Documented as an accepted risk in Deferred, not silently dropped. Revisit before production use or before this app handles real user data at scale.
